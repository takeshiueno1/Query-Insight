# 資料解析レポート

## 解析結果の要約

8件の一次資料は、プロダクトの目的、23画面（SCR-001〜SCR-023）、76 API行、DB・認証・監査の設計まで広くカバーしている。UIは1600×900を基準に、幅約200pxのサイドバー、64pxのトップバー、ダークネイビー／ブラック、黄色の主要アクション、カードとレーダーチャートを共通パターンとしている。

技術構成はJava 21、Spring Boot 4.1系、React 19.2系、Vite、Node.js 24 LTS、PostgreSQL 18.4で構成している。認証はRS256 JWT、短寿命Access Token、ローテーションするRefresh Token Cookie、Argon2id、RBAC＋データスコープを前提としている。

## 資料間の整合性

- 要件、画面、詳細設計で「社員・スキル・経歴・評価・管理」の機能分類は概ね一致する。
- SCR-001〜SCR-023の画面IDをルートに対応付けられる。
- 評価は「評価期」「評価対象」「評価基準バージョン」「評価明細」を分離する必要がある。
- 監査、楽観ロック、公開ID、状態遷移など、実務運用に必要な横断要件が記載されている。

## 検出した矛盾・欠落

### DB定義の混在

詳細設計書 `19_DBカラム` の `evaluation_targets` とされた行には、`version_name` や `grade_boundaries_json` など評価基準バージョンの列が入り、評価期・対象社員・評価者の対応列が不足している。名称と列責務が一致しないため、そのまま実装すると評価対象を表現できない。

初期スキーマでは次のように正規化した。

- `evaluation_criteria_versions`: 基準の版、名称、グレード境界
- `evaluation_criteria`: 版に属する評価項目と重み
- `evaluation_periods`: 評価期と期限
- `evaluation_targets`: 評価期、対象社員、評価者、状態、基準版

この判断は業務上自然な最小修正だが、正式な設計書改訂が必要である。

### 未確定の業務値

- グレード境界、評価項目の重み、端数処理
- 上長コメントを本人へ公開する時点と範囲
- 締切後、差戻し、代理評価、再提出の権限と状態遷移
- 退職者、評価履歴、監査ログ、添付証跡の保持期間
- メール、SSO、人事基幹連携の方式

### AI分析

画面・APIの構想に対し、ローカルOllamaとQwen3を採用した。API利用料と外部AIサービスへの送信は発生しない。AI入力は評価期間、能力軸、スキル、専門知識、直近の業務経験、確認済み資格に限定し、識別情報を除外する。本番ではOllamaサーバーの配置、容量、可用性、アクセス制御が別途必要である。

## 実装上の判断

- 全76 APIを薄く並べるのではなく、認証、社員、自己評価、通知、監査をDBまでつないだ縦断実装を優先した。
- 永続化はSpring JDBCの明示SQLとし、画面・API・テーブルの対応を追跡しやすくした。
- 本番はRSA鍵の設定がなければ起動失敗とし、エフェメラル鍵はテストとDockerローカル構成だけで明示的に許可する。
- UIは資料の視覚言語を再現しつつ、チャートの代替表、フォームラベル、レスポンシブ配置を追加した。

## リスクと優先順位
