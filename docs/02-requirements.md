# 要件

状態は今回の初期成果物に対する実装状況を示す。`実装済み` はAPI・DB・UIが接続済み、`画面骨格` はルーティングと表示のみ、`未実装` は後続対象である。

## データ要件

- APIには数値IDを公開せず、26文字ULIDを使用する。
- 社員番号、ログインID、スキルコード等は一意制約で二重登録を防ぐ。
- 評価基準はバージョン管理し、開始後の評価が後日の基準変更で変わらないようにする。
- 更新競合が業務上問題になる社員・評価データは `version` で楽観ロックする。
- 監査ログは業務データと分離し、利用者向けエラーと調査情報を分ける。

## 業務ルール

- ロールとデータスコープを別々に判定し、管理画面の表示だけに認可を依存しない。
- 自己評価は対象者本人、上長評価は割り当てられた評価者だけが操作できる。
- 提出・承認・差戻しの状態遷移はサーバー側で検証する。
- 上長は社員へ、経営者は上長へだけ差戻す。差戻し理由を必須とする。
- 上長評価は経営者の最終承認後だけ社員本人へ公開する。
- 締切後も操作を許可するが、警告を表示して期限超過を履歴へ記録する。
- 最終承認後は変更不可とし、`EXECUTIVE`だけが理由付きで上長評価へ再オープンできる。
- 代理操作は許可しない。

## 要件間の依存関係

認証・認可（FR-AUTH）が全機能の前提であり、評価（FR-EVAL）は社員・組織・評価基準・評価期に依存する。上長評価と経営者承認は、対象社員への評価者割当と`EXECUTIVE`ロールに依存する。AI分析（FR-AI）はデータ分類、契約、送信同意、保持方針の決定に依存する。
