# ダッシュボード・タレント情報・上長評価刷新 設計仕様

## 1. 目的

Query Insightの既存承認・履歴・監査機能を維持しながら、一般ユーザーが自分のスキル、得意分野、業務経歴、資格と、上長による正式評価を直感的に確認できる画面へ刷新する。

次を観測可能な完成条件とする。

- 添付されたQUERYロゴを基に、透明背景の「QUERY INSIGHT」ロゴがログイン画面と左メニューへ表示される。
- 一般ユーザーがスキル、得意分野、業務経歴、資格を種類別の画面から登録できる。
- 登録内容は直属上長の承認後だけ正式情報と自己ステータスへ反映される。
- 自己ステータスは本人が編集できず、承認済み情報からS/A/B/C/D/Fで自動算出される。
- 上長評価は役職者が直属部下について入力し、全社スコープを持つ役職者の最終承認後だけ本人へ公開される。
- AIが停止中でも、ルールベースの「プロトタイプ分析」をダッシュボードで実行できる。
- 利用者向け画面から画面IDや英語の内部パス表記を排除し、控えめなガラス調デザインで統一する。

## 2. 対象範囲

### 2.1 対象

- ログイン画面、共通レイアウト、左メニュー、パンくず、背景、カードの外観
- 一般ユーザー向けダッシュボード
- スキル・得意分野、業務経歴、資格の参照・登録導線
- 自己ステータスの算出と表示
- 役職者による上長評価入力と、一般ユーザーによる確定評価参照
- 評価基準と注意事項の上長評価画面内表示
- AI分析とルールベース代替分析
- 上長操作に起因する一般ユーザー向け通知と未読件数表示
- マスタ申請の種類・説明への簡略化
- 関連API、DB migration、監査、通知、テスト、トレーサビリティ文書

### 2.2 対象外

- 本番Ollamaの配置、性能保証、冗長化
- メール、SMS、外部チャットへの通知
- SSO、MFA、人事基幹システム連携
- 管理者による配点・ランク境界の画面変更
- AIによるランク決定または人事判断の自動化
- 管理者権限だけを根拠とした他社員のタレント情報・評価内容の閲覧
- 本番デプロイ、外部公開、実在社員データの登録

## 3. 権限と公開範囲

### 3.1 一般 `GENERAL / SELF`

- 自分のダッシュボード、スキル、得意分野、業務経歴、資格、確定済み上長評価、通知、マスタ申請を利用できる。
- 自己ステータスの点数・ランク・算出根拠は参照だけでき、編集できない。
- 自分が提出したタレント情報の下書き、申請、差戻し、履歴を扱える。
- 上長評価は最終承認済みの版だけ参照できる。

### 3.2 役職者 `OFFICER / SUBORDINATES`

- 一般権限の機能に加え、直属部下のタレント申請を承認・差戻しできる。
- 直属部下の上長評価を下書き保存、提出、再提出できる。
- 直属部下以外のタレント情報・評価は参照または更新できない。

### 3.3 全社役職者 `OFFICER / ALL`

- 上長が提出した個人単位の評価を最終承認・差戻し・理由付き再オープンできる。
- 最終承認前の内容は一般ユーザーへ公開しない。

### 3.4 管理者 `ADMIN`

- システム管理と監査機能を利用できる。
- `ADMIN`だけを理由に、他社員のタレント内容や評価内容を閲覧できない。

## 4. 情報設計と画面構成

### 4.1 一般ユーザーの左メニュー

1. ダッシュボード
2. スキル
3. 業務経歴
4. 資格
5. 上長評価
6. 通知
7. マスタ申請

通知には未読数を丸数字風のバッジで表示する。表示例は `①` 相当とし、実装は読み上げ可能な数値バッジを使用する。0件の場合はバッジを表示しない。99件を超える場合は `99+` とする。

役職者には権限とスコープに応じ、社員検索、上長評価入力、タレント承認、最終承認を追加する。管理者には監査・システム管理を追加する。

### 4.2 ダッシュボード

ダッシュボードへ次を集約する。

- プロフィール概要
- 自己ステータスの総合点と総合ランク
- スキル、得意分野、業務経歴、資格の分野別点数
- 承認済み情報を基にした能力バランス
- 未登録分野と算出根拠
- 最終承認済み上長評価の総合ランクと6軸
- AI分析実行ボタン
- 通常分析または「プロトタイプ分析」の結果
- 未読通知数

従来の「次にやること」は削除する。能力バランスと分析結果を横幅いっぱいに近い主要コンテンツとして表示する。「自己ステータス」と「AI分析」の独立メニュー・独立画面は一般ユーザーの主要導線から除外する。

### 4.3 スキル

同一画面内に「スキル」と「得意分野」の2区分を設ける。

- 承認済み一覧、申請中、差戻しの状態を混同せず表示する。
- 「スキルを登録」「得意分野を登録」の個別ボタンを配置する。
- 内部データ型 `SKILL` と `KNOWLEDGE` は維持し、`KNOWLEDGE` の利用者向け表示名だけを「得意分野」とする。
- 登録は種類ごとの入力フォームを開き、保存・直属上長への申請ができる。
- PDF/JPEG/PNGの根拠資料は任意とする。

### 4.4 業務経歴・資格

それぞれ専用画面と専用登録ボタンを持つ。

- 業務経歴には「業務経歴を登録」を表示する。
- 資格には「資格を登録」を表示する。
- 登録、下書き、申請、直属上長承認、差戻し、再申請、版履歴を維持する。

### 4.5 上長評価

一般ユーザーと役職者で同じ名称を使用し、内容を権限で切り替える。

- 一般ユーザーには最終承認済み評価と過去履歴だけを表示する。
- 役職者には直属部下一覧と評価入力を表示する。
- 全社役職者には提出済み評価の最終承認導線を表示する。
- 画面内にS/A/B/C/D/Fの意味、判断基準、評価上の注意事項を常時表示する。
- 独立した「評価基準」メニューは設けない。

### 4.6 マスタ申請

一般ユーザーの入力項目を次の2項目へ限定する。

- 種類
- 説明

状態、申請日時、管理者の判断結果、差戻し理由は履歴として表示する。既存データとの互換性が必要な内部項目は、migrationまたはサーバー側の既定値で吸収し、利用者へ不要な入力を求めない。

## 5. ブランドと外観

### 5.1 ロゴ

ユーザー提供画像のQUERY部分を編集対象として使用する。

- 元画像の黒・黄色の形状を維持する。
- 白背景を除去し、透明背景の正式アセットを作成する。
- QUERYの右側へ、黄色を基調とする太字の `INSIGHT` を追加する。
- ログイン画面では横長ロゴを大きく表示する。
- 左メニューでは同じロゴの縮小版を使用する。
- 狭幅では可読性を優先し、ロゴのシンボル部分または崩れない短縮表示へ切り替える。
- 画像生成・編集後は、文字列が正確に `QUERY INSIGHT` であること、白残り、輪郭欠け、不要な影がないことを目視確認する。

### 5.2 ログイン画面

次を削除する。

- 四角形の中にQIと書かれた装飾
- 「社員の経験と能力を、次の成長につなげる。」
- 「スキル・経歴・評価を一つに。」以下の説明
- 入力パネル上部のQIアイコン

ロゴ、ログイン見出し、ログインID、パスワード、ログインボタン、入力エラーだけを明確に配置する。既存のパスワード条件は変更しない。

### 5.3 控えめなガラス調

採用されたデザインAを基準とする。

- 暗い青黒色の背景と黄色アクセントを維持する。
- 背景に控えめな放射状グラデーションと低彩度の光彩を置く。
- カード、サイドバー、ヘッダーへ半透明背景、細い明色境界、軽いぼかしを適用する。
- 文字、フォーム、表、状態色のコントラストを低下させない。
- `backdrop-filter` が無効な環境では、不透明度の高い背景色へフォールバックする。
- 動きは既存のローディング等に限定し、常時動く装飾は追加しない。

### 5.4 日本語表記

- `QUERY INSIGHT / SKILLS/EDIT` のような英語パス表示を廃止し、日本語のページ名を表示する。
- `SCR-002`、`TALENT APPLICATION` 等の画面ID・内部名称は利用者画面に表示しない。
- DBやAPIの状態コードは日本語表示名へ変換し、コード値をそのまま表示しない。

## 6. 自己ステータス

### 6.1 入力データ

直属上長が承認し、正式反映された次のデータだけを使用する。

- スキル
- 得意分野
- 業務経歴
- 資格

申請中、差戻し、却下、失効した版は算出対象外とする。資格は有効期限が未設定または算出日時点で期限内のものだけを使用する。

### 6.2 分野別点数

各分野を0〜100点とする。

- スキル点：承認済みスキルの習熟度平均を、`習熟度 / 5 × 100` で換算する。
- 得意分野点：承認済み得意分野の習熟度平均を、`習熟度 / 5 × 100` で換算する。
- 業務経歴点：重複期間を二重加算しない承認済み経験月数を集計し、`min(経験月数 / 120 × 100, 100)` とする。
- 資格点：有効な承認済み資格1件を20点とし、`min(件数 × 20, 100)` とする。

該当データがない分野は0点とし、画面には「未登録」と表示する。

### 6.3 総合点とランク

総合点は次の加重合計とする。

`スキル点 × 0.40 + 得意分野点 × 0.20 + 業務経歴点 × 0.25 + 資格点 × 0.15`

内部計算は十分な精度を保ち、表示値は小数第1位へ四捨五入する。ランク判定は丸める前の値で行う。

| ランク | 境界 |
| --- | --- |
| S | 90点以上 |
| A | 80点以上90点未満 |
| B | 70点以上80点未満 |
| C | 60点以上70点未満 |
| D | 50点以上60点未満 |
| F | 50点未満 |

本人は分野別点数、総合点、ランクを編集できない。算出日時、使用した承認済みデータの識別子または版、式のバージョンを保持し、後から根拠を追跡できるようにする。

## 7. 上長評価

### 7.1 評価軸

役職者は直属部下について次の6軸を評価する。

- 技術力
- 設計力
- 業務理解
- 説明力
- 推進力
- 改善力

各軸はS/A/B/C/D/Fから選択し、軸別コメントと総評を入力する。画面に数値評価を表示しない。

### 7.2 総合ランク

軸別ランクを内部計算時だけ次の基準点へ変換する。

| ランク | 基準点 |
| --- | ---: |
| S | 100 |
| A | 85 |
| B | 75 |
| C | 65 |
| D | 55 |
| F | 0 |

6軸を等しい重みで平均し、自己ステータスと同じ境界で総合ランクを算出する。一般ユーザー向け画面と役職者向け入力画面には、変換後の数値を表示しない。

### 7.3 状態遷移と公開

既存の下書き、上長提出、最終承認、差戻し、再提出、再オープンを維持する。

- 上長の下書き・提出段階は本人へ非公開とする。
- 全社スコープを持つ役職者の最終承認後に、軸別ランク、軸別コメント、総合ランク、総評を本人へ公開する。
- 確定後は通常変更不可とし、全社スコープを持つ役職者だけが理由付きで再オープンできる。
- 旧確定版と、その時点の自己ステータス根拠を保持する。
- 版競合は409とし、監査ログと通知を同一トランザクション境界で記録する。

## 8. AI分析とプロトタイプ分析

### 8.1 共通入力

承認済みのスキル、得意分野、業務経歴、資格、自己ステータス、本人へ公開済みの上長評価だけを使用する。氏名、メール、社員番号、部署名、公開IDをモデル入力へ含めない。

### 8.2 通常分析

ローカルOllamaが利用可能な場合は既存の構造化出力検証、監査、保存を維持する。結果は強み、不足分野、推奨行動、要約に限定し、ランクや人事判断を決定しない。

### 8.3 プロトタイプ分析

Ollamaが無効、未起動、タイムアウト、接続不能の場合はルールベース分析へ自動切替する。

- 上位分野と高習熟度項目から強みを生成する。
- 0点または低得点分野から不足分野を生成する。
- 未登録分野には登録・更新を促す提案を生成する。
- 得意分野と業務経歴の組合せから、次に伸ばす候補を生成する。
- 画面へ「プロトタイプ分析」と明示し、AIが生成した結果と誤認させない。

ルールベース分析も入力スナップショット、生成方式、生成日時を監査可能にする。ルールベース処理自体が失敗した場合だけ、再実行ボタンと日本語エラーを表示する。

## 9. 通知

一般ユーザー向け通知は、上長または全社役職者による本人関連の次の操作で生成する。

- タレント申請の承認
- タレント申請の差戻し
- 上長評価の最終承認による公開
- 公開済み評価の理由付き再オープンまたは状態変更

通知にはタイトル、説明、発生日時、既読状態、対象画面への安全な内部リンクを持たせる。未読件数は通知一覧、左メニュー、ダッシュボードで同じAPI結果または同じキャッシュキーを共有し、既読化後に同期更新する。通知取得失敗は他機能を使用不能にせず、バッジを非表示として通知画面内で再取得を案内する。

## 10. API・データ設計方針

- 自己ステータス算出を単一責務のサービスへ分離する。
- ダッシュボード応答へ自己ステータス、分野別点数、算出根拠要約、確定上長評価、分析結果を追加する。
- タレント承認と同一トランザクション、または確実に再実行可能な処理で自己ステータスを再計算する。
- 上長評価APIはS/A/B/C/D/Fの列挙値を受け付け、範囲外の値を400で拒否する。
- 既存数値列を再利用する場合でもAPI・UIへ数値を露出せず、DB制約とmigrationでFを含む6段階を表現できるようにする。
- 評価版は軸別ランク、総合ランク、評価基準版、確定時点の自己ステータス根拠を保持する。
- 公開APIは本人、直属上長、全社スコープを必ず検証し、ロール名だけで許可しない。
- 既存の公開ID、楽観ロック、監査イベント、通知、版履歴を維持する。
- 既存クライアントとデータの移行方法をmigration内で明示し、破壊的な履歴削除を行わない。

## 11. エラー処理

- 未登録分野は0点として扱い、F表示と併せて未登録分野を明示する。
- 競合更新は409とし、最新状態の再取得を案内する。
- 権限不足は403、対象なしは情報露出を避けて適切に404または403とする。
- 入力不備は項目単位の日本語メッセージを表示する。
- 通知数取得失敗は主要画面を止めない。
- Ollama利用不能は通常エラー扱いにせず、プロトタイプ分析へ切り替える。
- 予期しない分析失敗は再実行可能な状態にし、内部例外や個人情報を画面へ表示しない。

## 14. 承認済み設計判断

- 自己ステータスは本人編集不可の参考値とする。
