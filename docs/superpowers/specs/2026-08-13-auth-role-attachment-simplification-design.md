# 認証・権限・任意添付の簡素化 設計仕様

## 1. 目的

利用者に見える権限を「一般」「役職者」「管理者」の3区分へ簡素化し、ログイン失敗回数によるアカウントロックを廃止する。タレント申請の根拠資料は任意であり、添付しない申請も正常に提出・承認できることを要件、API、画面、テストで一貫させる。

本変更後も、ログイン試行へのレート制限、失敗監査、短寿命JWT、Refresh Tokenローテーションと再利用検知は維持する。また、役職者のうち上長と社長が同じ操作を行える状態にはせず、データスコープで直属部下と全社を分離する。

## 2. 対象範囲

### 対象

- ログイン時の失敗回数加算、15分ロック、ロック中判定の廃止
- ロールコードと画面表示を `GENERAL`、`OFFICER`、`ADMIN` の3種類へ統合
- `OFFICER` の `SUBORDINATES` と `ALL` スコープによる上長・社長機能の分離
- 既存ロールと有効な権限付与の非破壊的な移行
- API認可、JWTロール、ナビゲーション、ローカルデータ、Bootstrap管理者の更新
- 添付なしのタレント申請を正式な正常系として明記・回帰テスト
- README、要件、ユースケース、セキュリティ、トレーサビリティの同期

### 対象外

- パスワードポリシー、JWT有効期限、Refresh Token仕様の変更
- ログインAPIのレート制限廃止
- 本番SSO・MFAの導入
- タレント添付の形式、件数、サイズ、ClamAV検査、閲覧認可の緩和
- 組織・アカウント管理画面の新規完成
- 本番デプロイ、外部公開、既存本番データへの直接操作

## 3. 権限モデル

### 3.1 表示ロール

| ロールコード | 表示名 | 基本用途 |
| --- | --- | --- |
| `GENERAL` | 一般 | 本人情報、自己評価、タレント申請、通知の利用 |
| `OFFICER` | 役職者 | 上長承認または社長の経営判断。対象範囲はスコープで限定 |
| `ADMIN` | 管理者 | 社員、組織、アカウント、マスタ、監査などのシステム管理 |

認証済み利用者は、ロールにかかわらず本人向けの基本操作を行える。`OFFICER` と `ADMIN` は一般機能へ追加の能力を持つ区分であり、一般機能のために `GENERAL` を重複付与しない。

### 3.2 役職者スコープ

| ロール | スコープ | 許可する主な操作 |
| --- | --- | --- |
| `OFFICER` | `SUBORDINATES` | 現在の直属部下の上長評価、タレント申請承認・差戻し、許可された根拠資料の閲覧 |
| `OFFICER` | `ALL` | 経営ダッシュボード、個人単位の最終承認、上長への差戻し、再オープン、全社対象の承認済み情報・許可された根拠資料の閲覧 |
| `ADMIN` | `ALL` | 管理機能、監査ログ、マスタ追加申請の承認・差戻し |

`OFFICER/SUBORDINATES` は全社APIを利用できず、`OFFICER/ALL` だけが従来の社長機能を利用できる。`ADMIN` は管理権限を持つが、それだけを理由に他社員のタレント内容や根拠資料を閲覧できない。管理権限と経営判断権限は引き続き分離する。

### 3.3 既存ロールの移行

| 既存ロール | 移行先 | スコープ・補足 |
| --- | --- | --- |
| `EMPLOYEE` | `GENERAL` | `SELF` |
| `MANAGER` | `OFFICER` | `SUBORDINATES` |
| `EXECUTIVE` | `OFFICER` | `ALL` |
| `SYSTEM_ADMIN`、`AUDITOR`、`HR` | `ADMIN` | `ALL`。管理機能の差を統合 |
| `SALES` | `GENERAL` | 特別な管理能力を付与しない |

Flywayでは新しい3ロールを追加し、有効な権限付与を重複なく新ロールへ移す。過去の監査・外部キー整合性を守るため旧ロール行は削除せず `INACTIVE` にする。移行後の認可とJWTは新ロールだけを使用する。

## 4. アカウントロック廃止

- ログイン失敗時に `failed_count` を増やさない。
- 5回失敗後の `locked_until` 設定を行わない。
- ログイン時に `locked_until` を参照しない。
- アカウントの `ACTIVE` / `INACTIVE` 状態判定は維持する。
- 存在しないログインIDとパスワード不一致は、従来どおり同じ401応答にする。
- パスワード照合時間を均すダミーハッシュ処理を維持する。
- ログイン成功・失敗の監査ログを維持する。
- IP・ログインID単位の既存レート制限を維持する。

既存DBとの互換性を優先し、`failed_count` と `locked_until` の列は今回削除しない。アプリからの参照・更新を停止し、移行時に残存するロック値を無効化する。将来の列削除は別の破壊的マイグレーションとして扱う。

## 5. 根拠資料の任意添付

- スキル、専門知識、資格、業務経歴は、根拠資料を1件も添付せず提出できる。
- 添付の有無は承認可否の必須条件にしない。
- 画面では「根拠資料（任意）」と表示する。
- 添付する場合だけ、PDF・JPEG・PNG、1件5MB以内、1申請3件までを適用する。
- 添付したファイルはCLEAN判定後だけ、本人、現在の直属上長、`OFFICER/ALL`へ公開する。
- 検査中・検査不能・感染判定のファイルが存在する場合は、そのファイルを安全に扱えないため提出を拒否する。ファイルを削除すれば添付なしで提出できる。

## 6. API・画面への影響

- JWTの `roles` claimは `GENERAL`、`OFFICER`、`ADMIN` のみを返す。
- 上長向けAPIは `OFFICER` と現在の直属部下関係を両方検証する。
- 社長向けAPIは `OFFICER` と有効な `ALL` スコープを両方検証する。
- 管理APIは `ADMIN` を検証する。
- ナビゲーションは3ロールとスコープに応じて表示する。ただし画面表示だけに認可を依存しない。
- `EXECUTIVE` 等を含む内部の評価状態名・監査アクション名・既存URLは、業務履歴とAPI互換性のため今回変更しない。
- 「MANAGER REVIEW」「EXECUTIVE REVIEW」等の利用者向け文言は、「役職者評価」「最終承認」などへ整理する。

## 7. エラー・安全性

- ロール不足は403、対象範囲外は情報秘匿のため404を維持する。
- 権限移行で同一アカウント・ロール・スコープの重複が生じる場合は1件へ正規化する。
- 役職者ロールだけを見て全社操作を許可しない。必ず `ALL` スコープを再確認する。
- 管理者ロールだけを見てタレント内容や添付を公開しない。
- アカウントロック廃止後もブルートフォース対策としてレート制限と監査を残す。

## 8. テスト方針

- 連続して誤ったパスワードを入力してもアカウントがロックされず、正しいパスワードでログインできること。
- ログイン失敗が毎回401かつ同一エラー形式で、監査記録が残ること。
- JWTが新しい3ロール以外を返さないこと。
- `OFFICER/SUBORDINATES` が直属部下を操作でき、非直属社員と全社APIを拒否されること。
- `OFFICER/ALL` が社長向け最終承認を行えること。
- `ADMIN/ALL` が管理・監査を行える一方、権限だけでは他社員のタレント内容・添付を読めないこと。
- 添付0件で4種類すべてを提出・承認できること。
- 添付した場合の形式、サイズ、件数、検査、閲覧認可が従来どおりであること。
- Backend全テスト、Frontend Lint・テスト・ビルド、Compose構文、可能な場合はローカルログインと主要3ロール導線を確認すること。

## 9. 移行・復旧

- DB変更は新ロール追加、権限付与の複製・正規化、旧ロールの無効化を順に行う。
- 旧ロール行を削除しないため、履歴参照と外部キーは維持される。
- ロールバックが必要な場合はアプリケーションを直前版へ戻し、旧ロールを再有効化して旧権限付与を利用できる。具体的な復旧SQLは実装計画で定義する。
- 本番適用は認証・認可設定の変更に該当するため、ローカル実装・検証完了後も別途実行直前の承認を必要とする。

## 10. 受け入れ条件

- ログイン失敗回数によるアカウントロックが発生しない。
- APIと画面に現れる権限が一般・役職者・管理者の3種類に統一される。
- 上長と社長の操作範囲がスコープで安全に分離される。
- 管理者と社長の権限が混同されない。
- 根拠資料なしでタレント申請を提出・承認できる。
- 添付した場合の安全制約は維持される。
- 要件、コード、テスト、トレーサビリティの記述が一致する。
