# Query Insight 全体要件・段階導入設計

- 作成日: 2026-08-11
- 状態: 要件・設計承認済み
- 対象: Query Insight 全体
- 前提: 現在の画面デザイン、React・Spring Boot・PostgreSQL・Docker Compose構成を継続利用する

## 1. 目的

社員情報、能力情報、年次評価を一元管理し、直属上長と社長が育成、配置、評価を判断できる状態を作る。人事は評価承認者、評価制度設定者、社員・組織管理者に含めない。

社員ランキングやAIによる自動評価は行わない。判断根拠、版、承認履歴を保持し、人が最終判断する。

## 2. 対象範囲

### 対象

- 認証、パスワード変更、管理者による再設定
- 社員、組織、所属、直属上長、アカウント管理
- 社員基本情報のExcel一括登録
- スキル、専門知識、資格、業務経歴の申請・承認・版管理
- 根拠資料の添付、認可付き閲覧、削除
- スキル・資格マスタの追加申請と管理
- 年次自己評価、上長評価、社長の最終承認
- 評価制度、期限、リマインドの年度別設定
- 経営ダッシュボード、前年度比較、配置判断用検索
- 本人向けAI育成助言と上長・社長への共有
- アプリ内通知、監査、退職者削除、バックアップ、復元

### 初期対象外

- 人事による評価承認
- 二次上長などの多段階評価承認
- 代理評価
- 複数人・複数申請の一括承認
- 社員ランキング
- Excel・CSV・PDFへの業務データ出力
- メール通知
- MFA、SSO
- AIによる点数、グレード、配置の自動決定
- 全機能のスマートフォン編集対応

## 3. 利用者と権限

| 利用者 | 権限 |
| --- | --- |
| 社員 | 自分の基本情報、タレント情報、申請、自己評価、確定評価、AI助言を参照する。タレント情報と自己評価を入力する。 |
| 直属上長 | 現在の直属社員だけを参照し、タレント申請の承認・差戻し、上長評価、配置検索を行う。 |
| 社長（`EXECUTIVE`） | 全社員の承認済みタレント情報、根拠資料、評価、AI助言を参照し、評価制度設定、最終承認、全社検索を行う。 |
| システム管理者 | 社員、組織、所属、アカウント、マスタ、評価制度を管理する。評価本文、根拠資料、AI助言は閲覧しない。 |
| 監査担当者 | 個人情報と評価自由記述を含まない監査ログだけを参照する。 |

監査ログは社長と監査担当者だけが閲覧する。既存の人事ロールには、本設計に基づく評価承認、評価制度設定、社員・組織管理権限を付与しない。

ロール判定とデータスコープ判定はAPI側で分けて行う。割当外の上長には対象の存在を秘匿して404、権限不足には403を返す。

## 4. 段階導入

### 第1段階: 社員・タレント情報管理

- 社員基本情報のExcel一括登録
- 社員・組織・アカウント管理
- タレント情報の申請、添付、上長承認、差戻し、版管理
- スキル・資格マスタ追加申請
- アプリ内通知と既読管理

第1段階を先行利用し、タレント情報を蓄積する。

### 第2段階: 年次評価・経営判断

- 年度別評価制度設定
- 自己評価、上長評価、社長最終承認
- 前年度比較、全社・部署別分布
- 配置判断用複合検索
- AI育成助言

評価機能は、第1段階の受入完了後に到来する最初の4月1日から正式利用する。

### 第3段階: 運用完成

- 仮パスワードと初回変更
- 自動リマインド
- 退職者自動削除
- 監査保持、バックアップ、復元確認
- 性能、ブラウザ、運用受け入れ試験

各段階は関連する自動テストと実動作確認が成功してから完了とする。
実装計画は段階ごとに分割し、最初の計画では第1段階だけを対象とする。

## 5. 社員・組織・アカウント管理

- 氏名、社員番号、所属、役職、直属上長はシステム管理者だけが更新する。
- 社員登録、アカウント無効化、部署の作成・変更・廃止、所属変更もシステム管理者だけが行う。
- 社員自身による基本情報の直接変更申請は設けない。
- 上長変更後は旧上長の閲覧・操作権限を失効し、新上長へ現在の直属社員スコープを付与する。
- 旧上長が作成した未提出の評価下書きは変更不能な履歴とし、新上長は新しい下書きを作成する。
- 新上長と社長は業務上必要な過去履歴を参照できるが、旧上長は上長変更後に参照できない。

## 6. タレント情報の申請・承認

対象はスキル、専門知識、資格、業務経歴のすべてとする。習熟度は1から5の5段階とする。

### 状態遷移

```text
DRAFT -> SUBMITTED -> APPROVED
                   -> RETURNED -> SUBMITTED
```

- 社員が入力して上長へ申請する。
- 上長は1件ずつ確認し、承認または理由付きで差戻す。
- 上長は申請内容や習熟度を直接変更しない。
- `APPROVED`だけを正式データとして検索・評価に使用する。
- 承認済み情報を変更する場合、旧版を正式データとして維持したまま新しい版を申請する。
- 新版承認後は旧版を変更不能な過去版として保持し、新版を正式データに切り替える。
- 申請、承認、差戻し、再申請を追記専用の業務履歴へ記録する。

### マスタ追加申請

- 社員は、必要なスキル・資格がマスタにない場合に追加申請できる。
- 社長またはシステム管理者が1件ずつ承認・差戻しする。
- 承認後に正式マスタとして選択可能にする。
- マスタの統合、名称変更、廃止は既存の利用履歴を破壊しない版・参照方式で行う。

## 7. 添付ファイル

- 対応形式はPDF、JPEG、PNGだけとする。
- 1ファイルの上限は5MB、1申請の上限は3ファイルとする。
- 拡張子、MIME Type、ファイルシグネチャ、サイズを検証する。
- アップロード直後は非公開の検査中状態とし、マルウェア検査に成功したファイルだけを閲覧可能にする。検査不能時は公開せず再試行対象とする。
- ファイル名を無害化し、レスポンスでは実保存先を公開しない。
- ファイル本体は初期構成ではPostgreSQLに保存し、申請、版、退職者削除、バックアップと一体管理する。
- 閲覧者は本人、現在の直属上長、社長だけとする。
- システム管理者、監査担当者、旧上長は閲覧できない。
- 認可済みAPIを経由して取得し、取得時に毎回ロールと現在の関係を再確認する。
- ブラウザへは安全なContent-Type、ダウンロード指定、キャッシュ制御を付ける。

## 8. 年次評価制度

- 評価対象期間は毎年4月1日から翌年3月31日までとする。
- 正式評価は年1回とする。
- 社長またはシステム管理者が前年設定を複製し、新年度設定を編集する。
- 評価項目、説明、並び順、1から5の尺度、重み、グレード境界、各締切、リマインド日時を年度別に設定する。
- 項目の重みは合計100%を必須とする。
- グレードはS、A、B、C、Dの5段階とし、境界値は年度ごとに設定する。
- 評価期開始後は評価項目、重み、グレード境界を変更できない。変更は次年度へ適用する。

## 9. 年次評価フロー

### 社員

- 各項目に1から5の自己評価点と根拠コメントを必須入力する。
- 年間総括コメントを必須入力する。
- 下書き保存、提出、上長差戻し後の修正・再提出を行う。

### 上長

- 各項目に1から5の上長評価点を入力する。
- 自己評価点と異なる項目は差分理由を必須とする。同点のコメントは任意とする。
- 年間総評を必須入力する。
- 理由付きで社員へ差戻すか、社長へ提出する。
- 提出後は社長から差戻されるまで編集できない。

### 社長

- 個人単位で最終承認する。一括承認は行わない。
- 承認コメントは任意とし、本人、現在の直属上長、社長へ公開する。
- 点数やグレードを直接変更しない。修正が必要な場合は理由付きで上長へ差戻す。
- 確定後は変更不可とする。訂正時は理由付きで再オープンし、上長評価へ戻す。
- 再オープンしても旧提出版、旧確定版、承認履歴を変更しない。

### 算出・公開

- 総合点は年度に固定された重みによる加重平均とする。
- 小数第3位を四捨五入し、小数第2位まで表示する。
- 年度の境界値からS、A、B、C、Dをサーバー側で決定する。
- 最終承認前は、社員へ上長点、差分理由、総評、承認コメントを公開しない。
- 最終承認後は、本人、現在の直属上長、社長だけが確定結果を参照する。
- 期限超過後も操作できるが、画面警告、通知、期限種別付き業務履歴を残す。
- すべての更新でversionを必須とし、古い画面、二重送信、不正遷移は409で拒否する。

## 10. 通知

- 通知手段はアプリ内通知だけとする。
- 通知を開いた時点で自動的に既読にする。
- タレント申請、承認、差戻し、再申請、自己評価提出、評価差戻し、上長評価提出、最終承認、再オープンを通知する。
- 評価期限のリマインド日時は年度ごとに社長またはシステム管理者が設定する。
- 期限前と期限超過後の通知を設定可能にする。
- 状態更新、履歴、監査、通知は同一トランザクションで確定する。
- 業務イベント単位の一意キーで通知重複を防止する。

## 11. 経営判断・検索・AI

### ダッシュボード

- 承認待ち、期限超過、確定済み件数を表示する。
- 当年度の全社・部署別グレード分布を表示する。
- 前年度と当年度を比較する。
- 社員ランキングは表示しない。

### 配置判断用検索

- スキル、資格、業務経験、確定評価を組み合わせて検索する。
- 社長は全社員、上長は現在の直属社員だけを検索する。
- 未承認のタレント情報は検索条件・結果に使用しない。
- 検索結果のファイル出力は行わない。

### AI育成助言

- AIは社員本人向けの育成アドバイスだけを生成する。
- 分析結果は本人、現在の直属上長、社長へ自動公開する。
- 点数、グレード、承認、配置を自動決定しない。正式評価の根拠には使用しない。
- 入力から氏名、メール、社員番号、公開IDなど直接識別子を除外する。
- 5分以内の完了を目標とし、完了・失敗をアプリ内通知する。
- 初期構成では外部AIへ社員情報を送信せず、ローカルOllamaを使用する。

## 12. 認証・監査

- 初期版はログインIDとパスワードによる認証を使用する。
- 操作用Access Tokenは15分、更新用セッションは8時間とする。
- 連続5回失敗で15分間ロックする。
- パスワードを忘れた場合、システム管理者が本人確認後に仮パスワードを発行する。
- 仮パスワードでの初回ログイン時は、新しいパスワードへの変更を必須とする。
- MFAとSSOは初期対象外とする。
- 重要な参照・更新・承認・認証・削除操作を監査する。
- 監査ログにToken、パスワード、添付本文、評価自由記述、AI助言本文を含めない。
- 監査ログは5年間保存する。

## 13. 退職者データ削除

- 退職日の30日後に自動削除する。
- 対象は社員基本情報、アカウント、評価結果、評価履歴、タレント情報、申請履歴、添付資料、AI分析結果、本人宛通知とする。
- 関連データを漏れなく特定して一つの削除処理単位で扱う。
- 削除結果は、個人を再識別できない匿名対象ID、削除日時、実行結果だけを監査ログへ5年間保存する。
- 削除失敗時は部分削除を完了扱いにせず、運用者へ通知して再実行可能にする。
- バックアップ内のデータは、バックアップ保存期限の到来時に順次消去する。

## 14. Excel初回移行

- 移行対象は社員基本情報だけとする。評価、スキル、資格、経歴は新規入力する。
- 指定テンプレートで氏名、社員番号、所属、役職、直属上長、ログインIDなどを受け付ける。
- 必須、長さ、形式、重複、部署、上長参照、循環上長関係を検証する。
- 1件でもエラーがあれば全件をロールバックする。
- 行番号、項目、エラーコード、利用者向け理由を一覧で返す。
- 実行者、ファイルのハッシュ、件数、結果を監査するが、ファイル内容をログへ出力しない。

## 15. UI・対応端末

- 現在のダークネイビー・ブラック、黄色の主要操作、カード・表中心のデザインを継続する。
- PCでは全機能をサポートする。
- スマートフォンでは閲覧、通知確認、自己評価をサポートする。
- 上長評価、社長承認、設定、管理操作はPC向けUIだけを提供する。これは対応UI範囲であり、認可は常にAPI側で行う。
- Chrome、Edge、Safariの各最新版を対象とする。
- スマートフォンは390px幅で横スクロール、操作不能、情報欠落がないことを確認する。

## 16. 非機能要件

| 項目 | 要件 |
| --- | --- |
| 利用者規模 | 社員50人以下 |
| 最大同時利用 | 25人程度 |
| 通常応答 | 25人同時利用時、AI・ファイル転送を除く画面表示・検索のp95を1秒以内 |
| AI応答 | 5分以内 |
| 稼働時間 | 原則24時間。夜間メンテナンスは事前通知 |
| アクセス範囲 | 社内ネットワークまたはVPNだけ |
| バックアップ | 週1回、3か月分保存 |
| データ損失許容 | 最大7日分 |
| 復旧目標 | 1営業日以内 |

バックアップは取得だけで完了とせず、定期的な復元試験でアプリ起動、認証、主要参照、添付取得を確認する。

## 17. エラー処理

- 400: 入力不足、形式、文字数、点数、重み合計、ファイル条件違反
- 401: 未認証、期限切れ、無効なセッション
- 403: ロール不足、データスコープ違反、送信元違反
- 404: 対象なし、または存在を秘匿する範囲外
- 409: 重複、状態遷移違反、楽観ロック、二重操作
- 413: ファイルまたはリクエスト容量超過
- 429: レート上限超過
- 500: 予期しない内部障害。利用者へ内部情報を返さない
- 503: AI、ストレージなど一時利用不可

既存のProblem Details形式とtraceIdを使用する。途中失敗時は、業務データ、履歴、通知、監査の整合性を保ってロールバックする。

## 18. テスト・受け入れ条件

### 機能・認可

- タレント申請、承認、差戻し、再申請、旧版保持が動作する。
- 上長は現在の直属社員だけを操作でき、上長変更時に権限が移る。
- 社員、旧上長、管理者、監査担当者が添付・評価を不正参照できない。
- マスタ追加申請を社長または管理者が1件ずつ処理できる。
- 自己評価から最終承認、差戻し、再オープンまでの全状態遷移が動作する。
- 最終承認前後で社員向け公開内容が切り替わる。
- AI結果は指定3者だけが参照でき、評価値を変更しない。

### 境界・異常系

- 1から5の上下限、必須コメント、最大文字数を検証する。
- 重み100%、丸め、SからDの各境界直前・一致・直後を検証する。
- version不一致、二重クリック、同時承認を409で拒否する。
- 添付の拡張子偽装、MIME不一致、マルウェア検出、5MB超過、4件目を拒否する。
- 通知、業務履歴、監査を重複させない。
- Excelの1行エラーで全件が未反映になる。
- 退職30日後に対象データが削除され、匿名監査だけが残る。

### UI・性能・運用

- Chrome、Edge、Safariで主要業務を確認する。
- PCと390pxスマートフォンの対応範囲を実画面で確認する。
- 25人相当の通常操作で1秒以内を確認する。
- AI分析が5分以内に完了または明確に失敗通知される。
- バックアップから1営業日以内に復元できる手順を実証する。

## 19. 既存実装からの主な変更

- スキル、資格、経歴を参照中心から申請・承認・版管理へ拡張する。
- 根拠ファイル保存と認可付き取得を追加する。
- 自己評価に年間総括を追加する。
- グレードをS・A・B・CからS・A・B・C・Dへ拡張する。
- 社長承認コメントを社員へ公開する。
- AI結果を本人だけでなく現在の直属上長と社長へ公開する。
- 年度設定、前年複製、リマインド、前年度比較を追加する。
- 通知を開いた時点で既読化する。
- パスワード再設定、Excel社員取込、退職者自動削除、復元運用を追加する。

既存の上長評価・経営者承認設計と矛盾する場合、本書で明示的に変更した事項は本書を優先する。既存データを破壊せず、Flywayによる前方追加と段階移行を基本とする。

## 20. 完了条件

- 第1段階の社員・タレント申請を実データで通し確認できる。
- 次の評価年度設定を複製・公開し、自己評価から社長承認まで実行できる。
- 権限、版、監査、通知、添付、削除が要件どおりに連動する。
- Backendテスト・ビルド、Frontend Lint・テスト・ビルドが成功する。
- Docker Composeで新規DBから起動し、主要HTTP・ブラウザ操作を確認できる。
- セキュリティ上の重大な未解決事項がない。
- バックアップ・復元・退職者削除の運用手順が再現可能である。
